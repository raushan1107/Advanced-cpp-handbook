C++ in the Wild

Every concept in this handbook, paired with one real place it actually gets used — a game, a bank, a browser, a robot arm — so "why would I ever use this?" has a concrete answer before you go looking for a bigger example on your own.

Covers: Module 0 → Module 10 + Best PracticesFormat: one topic, one domain, one sentence — not a tutorial

This page is a map, not a lesson: each entry names a real application domain and the one problem this concept solves there. Treat every entry as a research starting point — search the domain and the concept together, and you'll find the real system behind the one sentence.

How to use this page: next time you're deciding "should this be a unique_ptr or a raw pointer?", "should this be a virtual function or a template?", or "why would anyone need RTTI?" — find the concept here first. The domain example is the intuition; the module page is where you learn the syntax.

Module 0 — Foundation Enhancer

The concepts that decide how you think about a program before you've written a single class.

Procedural vs. object-oriented thinking

Game engines

Early engines (the Doom/Quake era) were written in C, faking "objects" with structs and function pointers. Modern engines model a GameObject/Component hierarchy in actual classes — the same jump this module makes.

Pointers

Embedded firmware / device drivers

A sensor driver on a microcontroller reads a hardware register through a raw pointer to a fixed memory address — there's no object, just an address, and dereferencing it wrong can corrupt the device.

Pass by value vs. pass by reference

Video editing software

A filter function takes a multi-megabyte video frame by reference to avoid copying it on every call, but takes a small "brightness" setting by value so the function can't accidentally change the caller's copy.

C vs. C++ (what changed, and why)

Legacy financial systems

Banks migrating old C risk-calculation engines to C++ keep the same math but wrap it in classes, so new compliance rules become overridable behavior instead of copy-pasted procedural code.

Module 1 — C++ Basics

The vocabulary every class in every later module is built from.

Classes & objects

E-commerce checkout

An Order class bundles items, price, and shipping status together, instead of five loose variables getting passed through every function that touches an order.

Access specifiers

Banking software

A BankAccount's balance is private — only deposit()/withdraw() can touch it, so nothing outside the class can set it to an invalid number directly.

Constructors & destructors

Database connection pools

A DbConnection opens in its constructor and is guaranteed closed in its destructor, so a connection is never silently leaked even if the calling code exits early.

Static members

Multiplayer game servers

A Player class keeps a static counter shared across every instance, so the server can report "14,203 players online" without a stray global variable.

Friend functions & classes

Graphics / physics engines

A Matrix class grants a Renderer class friend access to its raw internal floats for a direct GPU upload, without exposing that low-level access to everything else.

Module 2 — Inheritance & Polymorphism

How large systems treat many different things the same way — safely.

Inheritance

UI toolkits (Qt)

QPushButton, QCheckBox, and QLabel all inherit from QWidget, so the whole framework can lay out and repaint "anything on screen" uniformly, even though each one draws itself differently.

Virtual functions

Game engines

Every enemy type overrides a virtual update(); the engine's main loop calls it on a mixed list of enemies without an if/else chain asking "is this a Zombie? A Robot?" every single frame.

Abstract classes / pure virtual functions

Payment gateways

An abstract PaymentProcessor with a pure virtual charge() lets checkout code plug in Stripe, PayPal, or Razorpay interchangeably, never knowing which one it's actually talking to.

Virtual destructors & vtables

Plugin-based apps (audio/video editors)

A DAW loads third-party effect plugins as a base Effect*. Without a virtual destructor, deleting one through that base pointer runs only the base class's cleanup and leaks the plugin's real resources.

Module 3 — Compile-time Polymorphism

Choosing behavior at compile time, before a single object exists at runtime.

Function overloading

Math & graphics libraries

A vector-math library offers several dot() overloads for float, double, and int vectors, so every caller writes the same natural call regardless of precision.

Operator overloading

CAD / scientific computing software

A Matrix class overloads +, *, and == so engineering code reads result = A * B + C directly — the same notation the engineer already thinks in.

Module 4 — Exception Handling

What a program does the instant something it can't control goes wrong.

try/catch basics

Cloud storage apps (Dropbox-style)

An upload function wraps disk I/O in try/catch so a full disk or a permissions error becomes a clean "Upload failed" message instead of crashing the whole client.

Catch by type / multi-catch

Retail point-of-sale systems

A checkout terminal catches CardDeclinedException and NetworkTimeoutException separately, so it can say "Try another card" for one and "Check your connection" for the other.

Custom exceptions

Airline booking systems

SeatUnavailableException and FareExpiredException let a booking engine react to exactly which business rule broke, not just "something went wrong."

RAII

Industrial robotics

A robotic arm's MotorLock acquires a hardware lock in its constructor and releases it in its destructor, guaranteeing the motor is never left engaged if the control software crashes mid-operation.

Module 5 — Templates & Generics

Writing one algorithm that works for types you haven't thought of yet.

Why templates exist

Internal utility libraries

A single clamp<T>(value, min, max) works for int scores, float volume, and double sensor readings, instead of three near-identical hand-written functions.

Function templates

Game engines (math utilities)

A lerp<T>(a, b, t) smoothly animates a character's position, a camera's field of view, or a UI color — same formula, different type, zero duplicated code.

Class templates

Trading systems

A generic RingBuffer<T> stores the last N trades for one feed and the last N price ticks for another, using the exact same tested buffer logic for both.

STL as templates

Search engines / data pipelines

std::vector<Document> and std::unordered_map<string,int> (word-frequency counts) inside a search indexer are both instances of the exact template machinery you just learned.

Module 6 — STL & Containers

Picking the right data structure instead of reaching for an array every time.

Sequence containers

Game engines / music apps

A game keeps active bullets in a vector<Bullet> for fast iteration every frame; a music app keeps a deque<Track> playlist so it can queue or play-next from either end cheaply.

Associative containers

Browsers (DNS caching)

A browser's DNS cache is essentially an unordered_map<string, IPAddress> — look up a hostname and get its IP back in constant time instead of re-resolving it over the network.

Algorithms

E-commerce / analytics dashboards

An online store uses sort to rank products by rating, count_if to count what's in stock, and accumulate to total a cart — no hand-written loops.

Iterators

Log analysis tools

A log-monitoring tool scans a container with an iterator for error patterns, and the same scanning code keeps working unchanged even if the storage later swaps from a list to a vector.

Module 7 — Advanced C++ Features

The four features that turn a working program into a production-grade one.

Lambdas

UI event handling (Qt, game editors)

A "Save" button's click signal connects to a small inline lambda that captures the current document and writes it — no need to name a whole separate onSaveClicked() for one button.

Smart pointers

Game engines (asset management)

A texture is owned by a shared_ptr<Texture>; every 3D model using it holds a copy of that same pointer, and the texture is freed from GPU memory the instant the last model referencing it unloads.

File I/O

Games & editors (settings/config)

A game reads settings.json at startup with ifstream to restore resolution and key bindings, and writes it back with ofstream the moment a setting changes.

Multithreading

Video editors / ride-hailing apps

A video editor renders each timeline clip's thumbnail on its own thread so scrubbing stays smooth; a ride-hailing app's matcher uses a mutex to protect the shared "available drivers" list under concurrent requests.

Module 8 — Systems Programming & Advanced C++ Internals

What sits underneath the application layer — the OS, the network, the build.

Networking (TCP vs UDP)

Multiplayer games

A shooter sends player-position updates over UDP (fast, occasional loss is fine) but sends "match result" and "purchase confirmed" over TCP (must arrive) — the exact tradeoff this module teaches, live in production.

Move semantics

Photo/video editing pipelines

A photo editor passes a decoded 50MB bitmap between its "load," "filter," and "export" stages with std::move, handing it off instantly instead of copying it three times.

Pipes & file descriptors

Qt/QML industrial dashboards

An embedded Linux dashboard reads a temperature sensor's live output through a serial-port file descriptor and streams the readings straight into a QML gauge on screen.

Linking (static vs. dynamic)

Desktop game distribution

A studio dynamically links against a shared physics-engine .dll so a critical bug fix reaches every installed copy of the game through a small patch, not a multi-gigabyte reinstall.

Reading system info

Rendering engines

A game queries CPU core count at startup to decide how many worker threads to spawn for physics and AI, tuning itself automatically between a laptop and a high-end gaming PC.

RTTI (typeid, dynamic_cast)

Game engine editors / plugin systems

A level editor gets a generic Component* from a scene file and uses dynamic_cast to check "is this a LightComponent?" before showing light-specific sliders in the inspector.

Module 9 — Qt/QML & Network Programming

The GUI toolkit and networking classes behind a surprising number of applications you've probably already used.

Qt fundamentals & widgets

Cross-platform desktop software

VLC's player interface, Wireshark's packet inspector, and Autodesk Maya's entire UI are all built with Qt Widgets — the same QApplication/QWidget/layout pattern this module teaches, scaled up to a full production application.

Signals & slots

Automotive dashboards (Qt for Automotive)

A car's infotainment cluster built with Qt for Automotive lets the engine module emit a "gear changed" signal that updates the dashboard display — the dashboard code never needs to know the engine module exists at all.

QML & Qt Quick

Medical devices & industrial touchscreens

Ultrasound machines and industrial control-panel touchscreens use Qt Quick/QML specifically because it separates the visual design (QML) from the safety-critical logic (C++) — restyling the screen never risks touching the code that controls the hardware.

Qt networking

IoT gateways / remote monitoring dashboards

A factory-floor monitoring dashboard uses QTcpSocket to stream live sensor readings from a fleet of remote devices into one continuously-updating window — the same pattern this module's own Nimbus Fleet Console case study builds.

Game engines

Chromium (Chrome, Edge, Opera) · the V8 JavaScript engine

Web browsers

Parsing a page, laying it out, and running its JavaScript fast enough to feel instant — page after page, tab after tab — is built on a C++ core.

MySQL · MongoDB · Microsoft SQL Server

Databases

Adobe Photoshop · Autodesk Maya

High-frequency trading systems

Finance

ROS (Robot Operating System)

Robotics

⚠ Best Practices — Never Forget

A quick reminder, from Raushan: almost every resource this course teaches you to open, allocate, or lock also needs to be closed, freed, or unlocked — and nothing in C++ does that for you automatically unless you specifically reach for a tool that does. Every rule below traces back to a module you've already read; this tab exists so you never have to hunt for the reminder again.

The one habit that fixes most of this list: whenever you catch yourself pairing an "open" call with a manual "close" call, ask whether a Module 7/8 RAII tool (unique_ptr, shared_ptr, lock_guard, or just a destructor) could hold that resource instead — then the pairing enforces itself, even when an exception or an early return is in the way.
Module 7 · Smart Pointers

new → delete (and new[] → delete[])

Never forget: every new needs exactly one matching delete, and every new[] needs delete[] specifically (not plain delete). Miss it and that memory — and the object's destructor — is never reclaimed for the rest of the program's run.

Modern alternative: std::unique_ptr / std::make_unique. It deletes automatically the instant it goes out of scope, even if an exception unwinds straight through the function.

Module 7 · Smart Pointers

Multiple owners of one object → shared_ptr, not several raw pointers

Never forget: if more than one part of your program might need to keep an object alive, a raw pointer can't tell you who's responsible for the one delete — and calling it twice (a double free) crashes just as badly as never calling it.

Modern alternative: std::shared_ptr. Its reference count frees the object automatically the moment the last owner goes away — never earlier, never twice.

Module 7 · Smart Pointers

shared_ptr cycles (Parent ↔ Child) → break one side with weak_ptr

Never forget: two objects holding shared_ptrs to each other keep both reference counts above zero forever — a real leak, even though you did everything "right" with smart pointers.

Modern alternative: make the non-owning side (usually the "child looking back at its parent") a std::weak_ptr instead — it observes without counting as an owner, so the cycle breaks and both objects destruct correctly.

Module 8 · Networking

WSAStartup() → WSACleanup()

Never forget: every Winsock program on Windows must call WSAStartup() once before any socket call, and WSACleanup() once when networking is done — skip the cleanup and the Winsock library stays loaded and reference-counted past the point your program still needs it.

Modern alternative: Qt's networking classes (Module 9) hide this pairing entirely — QTcpSocket/QTcpServer need no WSAStartup/WSACleanup at all.

Module 8 · Networking

socket() → closesocket() (Windows) / close() (POSIX)

Never forget: an open socket holds a port and kernel resources for as long as your process runs — close every socket you open, on every code path, including the error paths.

Modern alternative: a small RAII wrapper (constructor opens, destructor closes) turns this into the same "can't forget it" guarantee fstream already gives you for files.

Module 8 · Pipes & FDs

CreatePipe / CreateProcess → CloseHandle for every HANDLE

Never forget: hRead, hWrite, hProcess, and hThread are four separate OS-tracked handles — leaving even one of them open leaks a kernel resource for the rest of the process's life, even after you've closed the other three.

Modern alternative: none built into the standard library for this one — Win32 handles are exactly the kind of resource a hand-written RAII wrapper class (constructor takes ownership, destructor calls CloseHandle) is meant for.

Module 7 · Multithreading

std::thread → .join() or .detach() before it destructs

Never forget: this one isn't a leak, it's a crash — a joinable std::thread whose destructor runs without either call terminates the entire program via std::terminate(), not just that one thread.

Modern alternative: decide up front whether the caller needs to wait for the thread (.join()) or truly doesn't (.detach()) — never leave a std::thread variable to just go out of scope unresolved.

Module 7 · Multithreading

std::mutex → don't call .lock()/.unlock() by hand

Never forget: an exception, an early return, or a break between a manual .lock() and .unlock() skips the unlock — the mutex stays locked forever, and every other thread that ever tries to lock it deadlocks.

Modern alternative: std::lock_guard / std::unique_lock. They unlock automatically in their destructor, even when an exception unwinds straight through the block — the RAII pattern applied to locking instead of memory.

Module 7 · File I/O

ifstream / ofstream — usually nothing to remember at all

Good news: fstream is already RAII — its destructor closes the file automatically when it goes out of scope, so you almost never need to call .close() yourself. The one time it matters: if you're about to reopen the same stream object for a different file while still in the same scope, close it explicitly first.

Why it's worth calling out: this is the pattern every rule above is trying to imitate — one object, acquire in the constructor, release in the destructor, nothing left to forget.

15-Smart_Pointers sample code

placement new → you must call the destructor yourself

Never forget: placement new only runs a constructor at memory you already own — there is no matching "placement delete" to free anything, so nothing will ever call that object's destructor for you.

Modern alternative: this is the one case in the whole course where you call a destructor directly by name (obj->~ClassName();) instead of relying on delete or scope-exit — reach for placement new only when you specifically need that control (memory pools/arenas), not as a general habit.
