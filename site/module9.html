Qt & Capstone / Module 9

Qt/QML & Network Programming

Every earlier module built logic that lived inside a terminal window. Qt is where that logic gets a face — windows, buttons, live text — and a way to talk to other machines without hand-rolling Winsock. This module covers the widget toolkit, the signals & slots pattern that holds a Qt program together, Qt Quick/QML's declarative alternative, and Qt's own networking classes.

Day: 6 of 6Topics: 4 + Story ModeCase study: Nimbus Fleet Console (chat GUI)Repo folder: 28-Qt-QML/
Before you start — install Qt: this module needs the Qt 6 SDK, which is not part of the plain g++ toolchain used everywhere else in this handbook. If you're on this repo's MSYS2/MinGW (UCRT64) setup, open the MSYS2 UCRT64 shell and run pacman -S mingw-w64-ucrt-x86_64-qt6-base mingw-w64-ucrt-x86_64-qt6-declarative mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja (roughly 300 MB installed). Otherwise, the Qt Online Installer gives you the same SDK with Qt Creator attached. Every code sample below was written, built, and (for the console/networking ones) actually run against this exact setup — Qt 6.10 via CMake + Ninja — before being put on this page.

A console program's entire interface is cout and cin. A desktop app needs a window, and a window needs something to keep it alive between clicks — Qt calls that the event loop, and everything else in this module is built on top of it.

WHY

Event-driven programs don't run top to bottom

Every program you've written so far runs main() top to bottom and exits. A GUI program can't work that way — it has to sit idle, doing nothing, until the user clicks something, then react, then go back to sitting idle. That waiting-and-reacting loop is the event loop: the operating system hands the application a stream of events (mouse clicks, key presses, window resizes), and the app's job is to respond to each one and then wait for the next.

Qt is a C++ framework built around that idea. QApplication owns the event loop; every visible thing on screen — a window, a button, a text field — is a QWidget or one of its subclasses; and app.exec() is the call that actually starts the loop and blocks until the user closes the app.

WHAT

QApplication, QWidget, and layouts

  • QApplication app(argc, argv) — exactly one per program, constructed at the top of main(). It parses Qt's own command-line arguments and owns the event loop.
  • QWidget — the base class for anything drawn on screen. A plain QWidget is a blank window; QPushButton, QLabel, QLineEdit, QTextEdit are all widgets that add their own drawing and behavior.
  • Layouts (QVBoxLayout, QHBoxLayout) — arrange child widgets vertically or horizontally and resize them automatically when the window resizes, instead of you calculating pixel positions by hand.
  • new QLabel(...) then layout->addWidget(label) — Qt widgets are heap-allocated with new and never manually deleted one by one; adding a widget to a layout makes the parent widget responsible for destroying it when the window closes. This is Qt's own ownership model, older than std::unique_ptr (Module 7) but solving the same problem: one clear owner for each resource.
  • window.show() — makes a widget visible; nothing appears on screen until this is called.
  • app.exec() — starts the event loop; the line after it doesn't run until the user closes the window.
HOW

A window with a label and a button that updates it

main.cpp
#include <QApplication>
#include <QWidget>
#include <QVBoxLayout>
#include <QLabel>
#include <QPushButton>

int main(int argc, char *argv[]) {
    QApplication app(argc, argv);

    QWidget window;
    window.setWindowTitle("Nimbus Click Counter");

    auto *layout = new QVBoxLayout(&window);
    auto *countLabel = new QLabel("Clicks: 0");
    auto *button = new QPushButton("Click me");

    layout->addWidget(countLabel);
    layout->addWidget(button);

    int clicks = 0;
    QObject::connect(button, &QPushButton::clicked, [&]() {
        clicks++;
        countLabel->setText(QString("Clicks: %1").arg(clicks));
    });

    window.show();
    return app.exec();
}

Note: that lambda passed to connect() is a first, informal look at Qt's signals & slots — clicked is a signal the button emits, and the lambda is the slot that runs in response. The next tab explains that connection properly, including how to declare your own signals.

A button doesn't know or care what happens when it's clicked — it just announces "I was clicked" and lets whoever's listening decide what to do. That announce/listen pattern is signals & slots, and it's the mechanism every Qt object uses to talk to every other Qt object without being tightly wired together.

WHY

Decoupling the announcer from the reactor

Without signals & slots, a button would need a direct reference to whatever it's supposed to update — "when clicked, call calculator.add(), then call label.setText()" — hardcoded inside the button's own click-handling code. That ties the button class to one specific use, and adding a second thing that should also react means editing the button.

Qt inverts this: a QObject declares a signal ("something happened") without knowing who, if anyone, is listening. Any number of other objects can connect() a slot — an ordinary function, lambda, or member function — to that signal. The emitter and the listener never need to know about each other's types beyond the signal's signature.

WHAT

Q_OBJECT, signals, slots, and connect()

  • Q_OBJECT — a macro at the top of any class that declares its own signals or slots. It marks the class for Qt's moc (Meta-Object Compiler), a code generator that runs before the real C++ compiler and writes the plumbing connect() needs. CMAKE_AUTOMOC ON runs moc for you automatically.
  • signals: — a section listing functions with no body; declaring one gives you emit signalName(args), which notifies every connected slot. Signals are never called directly, only emitted.
  • public slots: — in modern Qt, any regular member function, free function, or lambda can already be a slot; the slots: keyword is mostly there for readability and older Qt versions, but this repo keeps using it since it makes intent explicit.
  • QObject::connect(sender, &Sender::signalName, receiver, &Receiver::slotName) — the modern, type-checked connection syntax (a compile error if the signatures don't match, unlike Qt4's string-based SIGNAL()/SLOT() macros). receiver can be dropped when connecting straight to a lambda that doesn't need a QObject lifetime tied to it.
  • A class with Q_OBJECT defined inside a .cpp file (not its own header) needs one extra line at the bottom of that file — #include "main.moc" — so moc's generated code actually gets compiled in.
HOW

A Calculator object with its own signal, wired to two widgets

main.cpp
#include <QApplication>
#include <QWidget>
#include <QVBoxLayout>
#include <QHBoxLayout>
#include <QLineEdit>
#include <QPushButton>
#include <QLabel>

class Calculator : public QObject {
    Q_OBJECT
public:
    explicit Calculator(QObject *parent = nullptr) : QObject(parent) {}

public slots:
    void add(double a, double b) {
        emit resultChanged(a + b);
    }

signals:
    void resultChanged(double result);
};

int main(int argc, char *argv[]) {
    QApplication app(argc, argv);

    QWidget window;
    window.setWindowTitle("Nimbus Calculator");
    auto *outer = new QVBoxLayout(&window);

    auto *row = new QHBoxLayout();
    auto *inputA = new QLineEdit("2");
    auto *inputB = new QLineEdit("3");
    auto *addButton = new QPushButton("+");
    row->addWidget(inputA);
    row->addWidget(addButton);
    row->addWidget(inputB);
    outer->addLayout(row);

    auto *resultLabel = new QLabel("Result: (not calculated yet)");
    outer->addWidget(resultLabel);

    Calculator calc;
    QObject::connect(&calc, &Calculator::resultChanged, [&](double result) {
        resultLabel->setText(QString("Result: %1").arg(result));
    });

    QObject::connect(addButton, &QPushButton::clicked, [&]() {
        calc.add(inputA->text().toDouble(), inputB->text().toDouble());
    });

    window.show();
    return app.exec();
}

#include "main.moc"
Expected behaviorA window opens with two text fields (pre-filled "2" and "3"), a "+" button between them, and a result label below. Clicking "+" calls calc.add(...), which emits resultChanged(5), which the connected lambda uses to update the label to "Result: 5". Changing either field and clicking "+" again recalculates.

Everything so far describes the UI imperatively — construct a widget, add it to a layout, one line at a time. QML flips that: you declare what the UI looks like as data, and Qt Quick figures out how to draw and animate it. It's the same signals & slots engine underneath, viewed from a different, more designer-friendly language.

WHY

Declarative UI, and why it's a separate language

Widget code describes how to build a UI: create this label, add it to that layout, in this order. QML describes what the UI is: a window contains a column containing a text and a button — Qt Quick's own render engine handles the actual drawing, positioning, and animation. That declarative style is closer to HTML/CSS than to C++, and it's deliberate: a designer can edit .qml files without touching the C++ logic behind them, and Qt Quick's GPU-accelerated scene graph makes animations and touch interaction smoother than the widget toolkit was ever designed for.

C++ doesn't disappear — it becomes the backend: business logic, data, and anything performance-sensitive still lives in C++ classes, which QML talks to through the same signals & slots mechanism from the last tab.

WHAT

QML syntax and loading it from C++

  • import QtQuick / import QtQuick.Controls — QML's equivalent of #include, pulling in the visual element types used below.
  • Items (ApplicationWindow, Column, Row, Text, Button, TextField) — QML's version of widgets, nested as a tree using curly braces instead of C++'s layout objects.
  • Properties (width: 300, text: "hi") — name: value pairs inside an item; a property's value can itself be an expression that recalculates automatically whenever the values it references change (a binding), e.g. text: "Clicks: " + clicks.
  • Signal handlers (onClicked: clicks++) — QML's way of writing a slot inline, right where the signal is used, instead of a separate connect() call.
  • QQmlApplicationEngine + engine.load(QUrl::fromLocalFile("main.qml")) — the C++-side loader that reads a .qml file and builds the object tree it describes; QGuiApplication (not QApplication) is the right application object for a pure Quick app, since there's no widget toolkit involved.
  • engine.rootContext()->setContextProperty("name", &cppObject) — exposes one C++ QObject to QML under a name, so QML code can call its slots and react to its signals directly.
HOW

#include <QGuiApplication>

#include <QUrl>

int main(int argc, char *argv[]) {
    QGuiApplication app(argc, argv);

main.cpp — exposes Calculator to QML by name
#include <QGuiApplication>
#include <QQmlApplicationEngine>
#include <QQmlContext>
#include <QUrl>
#include <QObject>

class Calculator : public QObject {
    Q_OBJECT
public:
    explicit Calculator(QObject *parent = nullptr) : QObject(parent) {}
public slots:
    void add(double a, double b) { emit resultChanged(a + b); }
signals:
    void resultChanged(double result);
};

int main(int argc, char *argv[]) {
    QGuiApplication app(argc, argv);

    Calculator calc;
    QQmlApplicationEngine engine;
    engine.rootContext()->setContextProperty("calc", &calc);
    engine.load(QUrl::fromLocalFile("main.qml"));
    if (engine.rootObjects().isEmpty())
        return -1;
    return app.exec();
}

#include "main.moc"

Module 8 sent bytes with raw Winsock — WSAStartup, blocking recv(), manual buffer management, Windows-only. Qt wraps the same TCP/UDP ideas in QObjects that emit signals instead of blocking, so a network event fits into the exact same event loop a button click does — and the code is identical on Windows, Linux, and macOS.

WHY

Signals instead of blocking calls

Module 8's recv() blocks the whole thread until data arrives — fine for a simple one-shot demo, fatal for a GUI, where blocking the main thread freezes the window and stops it from repainting or responding to clicks. Qt's socket classes never block by default: instead of calling recv() and waiting, you connect() a slot to the socket's readyRead signal, and Qt calls it whenever data actually arrives — the event loop keeps servicing button clicks and window repaints in between.

The TCP-vs-UDP tradeoff from Module 8 is unchanged: QTcpSocket/QTcpServer for reliable, ordered delivery; QUdpSocket for cheap, connectionless, best-effort messages like a heartbeat.

WHAT

QTcpServer, QTcpSocket, and QUdpSocket

  • QTcpServer::listen(QHostAddress::Any, port) — starts listening; no separate bind()/listen() pair like raw sockets.
  • newConnection signal — emitted once per incoming client; server.nextPendingConnection() inside that slot returns the new QTcpSocket* for that client.
  • readyRead signal — emitted whenever a socket has bytes waiting; socket->readAll() reads everything available as a QByteArray.
  • socket->write(data) — queues bytes to send; like send() but never blocks the caller.
  • connected / disconnected signals — fire when a QTcpSocket's connection state changes; no manual "did connect() succeed?" check needed.
  • QUdpSocket::bind(...) then writeDatagram(data, address, port) / readDatagram(buffer, size) — UDP's connectionless send/receive, still wired through the same readyRead signal.
  • No WSAStartup/WSACleanup, no -lws2_32 — Qt's Network module hides the platform socket API entirely: find_package(Qt6 REQUIRED COMPONENTS Network) and target_link_libraries(... Qt6::Network) is all the build needs.
HOW

A console TCP chat server and client, no widgets involved

chat_server.cpp
#include <QCoreApplication>
#include <QTcpServer>
#include <QTcpSocket>
#include <QTextStream>

int main(int argc, char *argv[]) {
    QCoreApplication app(argc, argv);
    QTextStream out(stdout);

    QTcpServer server;
    if (!server.listen(QHostAddress::Any, 9091)) {
        out << "Failed to start server: " << server.errorString() << "\n";
        return 1;
    }
    out << "[Server] Listening on port 9091...\n";
    out.flush();

    QObject::connect(&server, &QTcpServer::newConnection, [&]() {
        QTcpSocket *client = server.nextPendingConnection();
        out << "[Server] Client connected.\n";
        out.flush();

        QObject::connect(client, &QTcpSocket::readyRead, [client, &out]() {
            QByteArray data = client->readAll();
            out << "[Server] Received: " << data << "\n";
            out.flush();
            client->write("Message received, over.");
        });

        QObject::connect(client, &QTcpSocket::disconnected, client, &QTcpSocket::deleteLater);
    });

    return app.exec();
}
chat_client.cpp
#include <QCoreApplication>
#include <QTcpSocket>
#include <QTextStream>

int main(int argc, char *argv[]) {
    QCoreApplication app(argc, argv);
    QTextStream out(stdout);

    QTcpSocket socket;
    QObject::connect(&socket, &QTcpSocket::connected, [&]() {
        out << "[Client] Connected to server.\n";
        out.flush();
        socket.write("Rack-A temperature nominal.");
    });
    QObject::connect(&socket, &QTcpSocket::readyRead, [&]() {
        out << "[Client] Server replied: " << socket.readAll() << "\n";
        out.flush();
        app.quit();
    });

    socket.connectToHost("127.0.0.1", 9091);
    return app.exec();
}

🎬 Story Mode

The on-call engineer who wanted a window, not a log file

Nimbus Systems' fleet diagnostics relay from Module 8 works — reports arrive over TCP, critical events are flagged, nothing gets lost. But the on-call engineer still reads it as scrolling text in a terminal at 2am, squinting for the word CRITICAL. The ops lead's ask was blunt: "give them something they can glance at." Here's how the team built that, one Qt concept at a time.

ACT 1

"First, just get a window on screen"

The first prototype was almost embarrassingly small: one label, one button, proof that a Qt window could open and redraw itself without crashing. That's deliberately where the team started too — before wiring anything real, they needed to trust the basic loop of "show a window, click something, see it update" on their own machines.

ACT 2

"The console can't know about the parser, and vice versa"

Early on, someone wired the report parser to call a specific MainWindow::updateLog() method directly. It worked, until a second panel needed the same data and the parser had to learn about two window classes instead of zero. Switching the parser to emit reportParsed(text) and letting each panel connect() independently meant the parser never has to change again, no matter how many panels the ops team adds.

ACT 3

"The wall display needed a different skin, not different logic"

The ops room wanted a big wall-mounted status board — legible from across the room, touch-friendly, restyled every few months as the team's taste changed. Rebuilding the C++ widget layout for that would mean recompiling for every visual tweak. Instead, the same Calculator-style backend objects got a QML front end: designers now edit .qml files to change the wall display's look without anyone touching the C++ that decides what's critical.

ACT 4

"The console finally talks to the relay live"

The last piece connected the window to Module 8's actual relay server: a QTcpSocket inside the console widget, its readyRead signal wired straight to the same log panel from Act 2. No blocking recv() loop freezing the window mid-update — reports simply appear as they arrive, exactly the "glance at it" experience the ops lead asked for.

A button doesn't need to know who's listening. A signal doesn't need to know who's watching. And a window that never blocks is a window an on-call engineer can actually trust at 2am.

AutomotiveIn-car infotainment systems render their touch UI in QML while the CAN-bus/vehicle-signal logic stays in C++, for the same "designers iterate without a rebuild" reason.

Step 2A custom signal drives a label

The Tab 2 Calculator, minus the second input — one signal, one emit, one connected slot.

step2_signal.cpp
#include <QApplication>
#include <QWidget>
#include <QVBoxLayout>
#include <QPushButton>
#include <QLabel>

class Pinger : public QObject {
    Q_OBJECT
public:
    explicit Pinger(QObject *parent = nullptr) : QObject(parent) {}
public slots:
    void ping() { emit pinged("pong"); }
signals:
    void pinged(QString reply);
};

int main(int argc, char *argv[]) {
    QApplication app(argc, argv);
    QWidget window;
    auto *layout = new QVBoxLayout(&window);
    auto *label = new QLabel("Waiting...");
    auto *button = new QPushButton("Ping");
    layout->addWidget(label);
    layout->addWidget(button);

    Pinger pinger;
    QObject::connect(&pinger, &Pinger::pinged, [&](QString reply) { label->setText(reply); });
    QObject::connect(button, &QPushButton::clicked, [&]() { pinger.ping(); });

    window.show();
    return app.exec();
}

#include <QCoreApplication>
#include <QTcpSocket>
#include <QTextStream>

int main(int argc, char *argv[]) {
    QCoreApplication app(argc, argv);
    QTextStream out(stdout);
    QTcpSocket socket;
    QObject::connect(&socket, &QTcpSocket::connected, [&]() {
        out << "Connected to relay.\n";
        app.quit();
    });

        out << "Could not reach relay (start chat_server.exe first).\n";
        app.quit();
    });
    socket.connectToHost("127.0.0.1", 9091);

Nimbus Fleet Console — widgets, a custom-feeling connection, and live networking together

A chat-style window: a read-only log, a text field, a Send button, and a QTcpSocket wired straight into the same log via signals.

program.cpp — complete use case
#include <QApplication>
#include <QWidget>
#include <QVBoxLayout>
#include <QHBoxLayout>
#include <QLineEdit>
#include <QPushButton>
#include <QTextEdit>
#include <QTcpSocket>

class NimbusChatClient : public QWidget {
    Q_OBJECT
public:
    NimbusChatClient() {
        setWindowTitle("Nimbus Fleet Console");
        resize(360, 280);

        auto *outer = new QVBoxLayout(this);
        log = new QTextEdit();
        log->setReadOnly(true);
        outer->addWidget(log);

        auto *row = new QHBoxLayout();
        input = new QLineEdit();
        auto *sendButton = new QPushButton("Send");
        row->addWidget(input);
        row->addWidget(sendButton);
        outer->addLayout(row);

        connect(&socket, &QTcpSocket::connected, this, [this]() {
            log->append("[System] Connected to relay.");
        });
        connect(&socket, &QTcpSocket::readyRead, this, [this]() {
            log->append("[Relay] " + QString::fromUtf8(socket.readAll()));
        });
        connect(sendButton, &QPushButton::clicked, this, [this]() {
            QString text = input->text();
            if (text.isEmpty()) return;
            socket.write(text.toUtf8());
            log->append("You: " + text);
            input->clear();
        });

        socket.connectToHost("127.0.0.1", 9091);
    }

private:
    QTextEdit *log;
    QLineEdit *input;
    QTcpSocket socket;
};

int main(int argc, char *argv[]) {
    QApplication app(argc, argv);
    NimbusChatClient window;
    window.show();
    return app.exec();
}
