Wrap-up & Evaluation

Three mini-projects that each lean on a different slice of everything you've built so far — a Banking System (safety and exceptions), a Library Management System (persistence and STL), and a Qt Shape Drawing canvas (rendering Module 2's polymorphic shapes) — plus a look at whether your code is actually fast, and how to present it once it's done.

How this module is organized: the Banking System, Library Management System, and Shape Drawing canvas are three independent mini-projects, not one merged program — each is a small, complete, worked example of a pattern real teams reuse for much larger versions of the same system. The Library Management System is this module's flagship "Try now" build, since it's the one that needs nothing beyond the plain g++ toolchain already used all course long; Shape Drawing needs the Qt SDK from Module 9.

A banking system is the classic first "real" C++ project because it forces three earlier modules to work together at once: inheritance for account types, exceptions for the operations that must never silently fail, and smart pointers for a collection that owns its accounts safely.

WHY

Money is the use case that makes "just don't crash" not good enough

A withdrawal that overdraws an account, or a deposit of a negative amount, isn't a crash-worthy bug — it's a silent, wrong answer that looks like a valid balance. Module 4's exception handling exists exactly for cases like this: instead of returning a sentinel value the caller might forget to check, an invalid operation throws, and the caller is forced to either handle it or let it propagate — it cannot be silently ignored the way a returned error code can.

A transfer between two accounts adds a second requirement: if the withdrawal from the source account fails, the deposit into the destination must never happen. Ordering the two calls so the risky one (withdraw) runs first, and only calling deposit if it didn't throw, keeps the two accounts consistent even when something goes wrong.

WHAT

A small class hierarchy, one custom exception, and unique_ptr ownership

  • class InsufficientFundsError : public runtime_error — a custom exception type (Module 4) that carries a specific, catchable meaning instead of a generic runtime_error every caller has to inspect the message of.
  • Account / SavingsAccount : public Account — the same base/derived relationship from Module 2, this time modeling a real account hierarchy instead of shapes.
  • vector<unique_ptr<Account>> — the bank owns every account exactly once (Module 7); storing base-class pointers lets the vector hold a mix of Account and SavingsAccount objects polymorphically.
  • dynamic_cast<SavingsAccount*>(ptr) — Module 8's RTTI, used here to reach a SavingsAccount-only method (applyInterest()) from a loop that's iterating over the base type.
HOW

Transfer between accounts, then trigger and catch an overdraft

banking_system.cpp
#include <iostream>
#include <string>
#include <vector>
#include <memory>
#include <stdexcept>
#include <sstream>
#include <iomanip>
using namespace std;

class InsufficientFundsError : public runtime_error {
public:
    InsufficientFundsError(const string& msg) : runtime_error(msg) {}
};

class Account {
protected:
    string owner;
    double balance;
public:
    Account(string owner_, double opening) : owner(move(owner_)), balance(opening) {}
    virtual ~Account() {}
    virtual void deposit(double amt) {
        if (amt <= 0) throw invalid_argument("Deposit amount must be positive");
        balance += amt;
    }
    virtual void withdraw(double amt) {
        if (amt <= 0) throw invalid_argument("Withdrawal amount must be positive");
        if (amt > balance) throw InsufficientFundsError(owner + " has insufficient funds");
        balance -= amt;
    }
    double getBalance() const { return balance; }
    virtual string describe() const {
        ostringstream oss;
        oss << owner << ": $" << fixed << setprecision(2) << balance;
        return oss.str();
    }
};

class SavingsAccount : public Account {
    double rate;
public:
    SavingsAccount(string owner_, double opening, double rate_) : Account(move(owner_), opening), rate(rate_) {}
    void applyInterest() { balance += balance * rate; }
    string describe() const override {
        ostringstream oss;
        oss << owner << " (Savings, " << int(rate * 100) << "% APR): $" << fixed << setprecision(2) << balance;
        return oss.str();
    }
};

void transfer(Account& from, Account& to, double amt) {
    from.withdraw(amt); // if this throws, `to` is untouched
    to.deposit(amt);
}

int main() {
    vector<unique_ptr<Account>> bank;
    bank.push_back(make_unique<Account>("Meera", 500.0));
    bank.push_back(make_unique<SavingsAccount>("Aakash", 1000.0, 0.04));

    cout << "Opening balances:\n";
    for (auto& acc : bank) cout << "  " << acc->describe() << "\n";

    transfer(*bank[1], *bank[0], 200.0);
    cout << "\nAfter transferring 200 from Aakash to Meera:\n";
    for (auto& acc : bank) cout << "  " << acc->describe() << "\n";

    if (auto* savings = dynamic_cast<SavingsAccount*>(bank[1].get())) {
        savings->applyInterest();
    }
    cout << "\nAfter Aakash's savings account applies interest:\n";
    for (auto& acc : bank) cout << "  " << acc->describe() << "\n";

    cout << "\nAttempting to withdraw 10000 from Meera's account:\n";
    try {
        bank[0]->withdraw(10000.0);
    } catch (const InsufficientFundsError& e) {
        cout << "  Caught: " << e.what() << "\n";
    }
}

A library catalog is a small STL-and-file-I/O project: a collection of records, a couple of state changes (borrowed vs. available), and — the part most console-only class exercises skip — actually surviving the program exiting and starting again.

WHY

In-memory state disappears the moment the program exits

Every earlier module's programs built a vector or a map, printed something useful from it, and exited — the data was never meant to outlive one run. A real catalog has to survive that: close the program, reopen it tomorrow, and the same books, with the same borrowed/available state, need to still be there. That's what Module 7's file I/O is actually for in a system like this — not just "reading a file," but giving a program memory across separate runs.

WHAT

A simple delimited file format, plus find_if for lookups

  • struct Book { string title, author; bool onLoan; } — a plain aggregate; no need for a class hierarchy here since every book is the same kind of record.
  • find_if(catalog.begin(), catalog.end(), lambda) — Module 6's algorithm header, used here to locate one book by title without writing a manual loop.
  • Delimited text format — each line is title|author|0-or-1; ofstream writes it, ifstream + getline(stream, field, '|') reads it back field by field. This is the simplest possible persistence format — real systems would reach for a library like SQLite (already a dependency of Qt6, from Module 9's install) or a structured format like JSON once the schema grows past a few fields.
HOW

Module 2 built a Shape/Circle/Rectangle hierarchy that only ever printed area() to a console. Give that same polymorphic hierarchy one more virtual method — draw() — and Module 9's Qt skills turn it into an actual picture.

WHY

Rendering is just another virtual call

Nothing about polymorphism changes when the thing each subtype does differently is "draw itself" instead of "compute my area." Shape gains a second pure-virtual method, draw(QPainter&), and every subclass implements it the same way it already implements area() — the calling code still just loops over vector<unique_ptr<Shape>> and calls a virtual method, exactly like Module 2 and Module 8's RTTI examples did.

What's new is when that loop runs: a QWidget doesn't paint itself once and stay that way — the OS asks it to repaint whenever it's shown, resized, or uncovered, and Qt calls paintEvent() each time that happens.

WHAT

paintEvent, QPainter, and scheduling a redraw

  • void paintEvent(QPaintEvent*) override — a QWidget virtual method Qt calls whenever the widget needs to (re)draw; you never call it yourself.
  • QPainter painter(this) — constructing a painter "on" a widget inside paintEvent is what makes its draw* calls actually land on that widget's surface.
  • painter.setBrush(Qt::cyan) / drawEllipse(...) / drawRect(...) — fill color plus the actual shape-drawing calls; QPainter::Antialiasing smooths curved edges.
  • widget->update() (not used in this minimal demo, but the standard next step) — schedules a repaint for later rather than drawing immediately, so multiple changes in one event can be batched into a single paintEvent call.
HOW

The Module 2 Shape hierarchy, rendered instead of printed

main.cpp
#include <QApplication>
#include <QWidget>
#include <QPainter>
#include <memory>
#include <vector>
using namespace std;

struct Shape {
    virtual ~Shape() {}
    virtual double area() const = 0;
    virtual void draw(QPainter &painter) const = 0;
};

struct Circle : Shape {
    int x, y, radius;
    Circle(int x_, int y_, int r) : x(x_), y(y_), radius(r) {}
    double area() const override { return 3.14159 * radius * radius; }
    void draw(QPainter &painter) const override {
        painter.setBrush(Qt::cyan);
        painter.drawEllipse(QPoint(x, y), radius, radius);
    }
};

struct RectangleShape : Shape {
    int x, y, w, h;
    RectangleShape(int x_, int y_, int w_, int h_) : x(x_), y(y_), w(w_), h(h_) {}
    double area() const override { return w * h; }
    void draw(QPainter &painter) const override {
        painter.setBrush(Qt::yellow);
        painter.drawRect(x, y, w, h);
    }
};

class ShapeCanvas : public QWidget {
public:
    ShapeCanvas() {
        shapes.push_back(make_unique<Circle>(80, 80, 50));
        shapes.push_back(make_unique<RectangleShape>(180, 40, 100, 80));
        setWindowTitle("Nimbus Shape Canvas");
        resize(320, 200);
    }
protected:
    void paintEvent(QPaintEvent *) override {
        QPainter painter(this);
        painter.setRenderHint(QPainter::Antialiasing);
        for (const auto &s : shapes) s->draw(painter);
    }
private:
    vector<unique_ptr<Shape>> shapes;
};

int main(int argc, char *argv[]) {
    QApplication app(argc, argv);
    ShapeCanvas canvas;
    canvas.show();
    return app.exec();
}

Every program in this course so far has been judged on one thing: does it produce the right output? The last skill before you ship anything is the other question — is it fast enough, and if not, exactly where is the time going?

WHY

"It feels slow" is not a diagnosis

Guessing at performance problems wastes time on the wrong fix. The discipline is: measure first, change one thing, measure again — the exact same "predict, run, compare" rhythm this handbook has used for every topic, applied to wall-clock time instead of program output. Two of the most common, easy-to-miss costs in C++ specifically are container reallocation (a vector growing without reserve() copies every existing element into new memory, repeatedly) and unnecessary copies (Module 8's move semantics exists specifically to avoid this one).

WHAT

Manual timing, and the real profiling tools for when manual timing isn't enough

  • std::chrono::high_resolution_clock::now() — Module 7-adjacent standard-library timing; bracket the code under test with two calls and subtract.
  • duration<double, milli> — converts a raw tick difference into milliseconds as a plain double you can print.
  • gprof — the classic GCC/MinGW profiler: compile with -pg, run the program once (it writes a gmon.out file), then run gprof yourprogram.exe gmon.out to get a per-function breakdown of where time actually went, instead of guessing.
  • Visual Studio Performance Profiler — for MSVC projects, Debug → Performance Profiler → CPU Usage gives the same kind of per-function timing breakdown with a graphical call tree, no separate command-line tool needed.
  • Valgrind/callgrind (Linux/macOS) — a heavier but very precise instruction-level profiler; overkill for a quick check, valuable for a genuinely mysterious bottleneck.
HOW

Measuring the exact cost of skipping reserve()

performance_debugging.cpp
#include <iostream>
#include <chrono>
#include <vector>
using namespace std;
using namespace std::chrono;

vector<int> buildWithoutReserve(int n) {
    vector<int> v;
    for (int i = 0; i < n; i++) v.push_back(i);
    return v;
}

vector<int> buildWithReserve(int n) {
    vector<int> v;
    v.reserve(n);
    for (int i = 0; i < n; i++) v.push_back(i);
    return v;
}

int main() {
    const int N = 2000000;

    auto t1 = high_resolution_clock::now();
    auto v1 = buildWithoutReserve(N);
    auto t2 = high_resolution_clock::now();
    auto v2 = buildWithReserve(N);
    auto t3 = high_resolution_clock::now();

    duration<double, milli> withoutReserve = t2 - t1;
    duration<double, milli> withReserve = t3 - t2;

    cout << "Without reserve(): " << withoutReserve.count() << " ms\n";
    cout << "With reserve():    " << withReserve.count() << " ms\n";
    cout << "Both vectors have size " << v1.size() << " and " << v2.size() << "\n";
}
Actual output (your numbers will vary by machine and by run — timing is never perfectly repeatable)Without reserve(): 23.3903 ms With reserve(): 9.0513 ms Both vectors have size 2000000 and 2000000

Run it and experiment

  1. Compile: g++ -std=c++17 performance_debugging.cpp -o performance_debugging, run it two or three times and watch the numbers shift slightly each time — that variance is normal and is exactly why profiling tools average over many runs instead of trusting one.
  2. Experiment 1: Compile again with -O2 and compare — optimized builds shrink the gap, but reserve() still wins, because it's avoiding real reallocations the optimizer can't remove.
  3. Experiment 2 (gprof): Recompile with g++ -std=c++17 -pg performance_debugging.cpp -o performance_debugging, run it once, then gprof performance_debugging.exe gmon.out — look for buildWithoutReserve and buildWithReserve in the flat profile and confirm which one the tool itself reports as more expensive.

A working program is not the same skill as explaining one. In an enterprise team, "it compiles and passes review" only matters once you can also walk a room through what it does, why you built it that way, and what you'd change with more time — that's the actual job once training ends.

WHY

Reviews and demos are where design decisions get tested

A design decision that seemed obvious while you were writing the code — why transfer() withdraws before it deposits, why the shape hierarchy uses a virtual draw() instead of a big switch — often only gets questioned out loud in a review or a demo. Being able to defend it in one or two sentences, with the actual tradeoff, is a large part of what separates "I wrote code that works" from "I can be trusted with a codebase other people depend on."

WHAT

A short presentation checklist

  • Problem statement (1-2 minutes): what does this solve, and for whom — before any code is shown.
  • Architecture walkthrough (3-4 minutes): the class/module shape, not every function — a whiteboard sketch of Shape → Circle/Rectangle says more in ten seconds than scrolling through the header file.
  • Live demo, not just slides (4-5 minutes): run the actual program. A demo that fails live and gets debugged in front of the room is more convincing than a screenshot, not less.
  • One deliberate edge case (2 minutes): show a case you thought about on purpose — an overdrawn account, a missing catalog file, a division by zero — and how the program handles it without crashing.
  • What you'd do differently (1-2 minutes): naming a real tradeoff you made under time pressure (the delimited file format instead of SQLite, say) shows judgment, not just output.

🎬 Story Mode

Launch day at Nimbus

Six days ago this cohort couldn't compile "hello world." Today, Nimbus's engineering lead has asked three of them to demo what they built during training to the rest of the department — not as an exercise, but because the department actually wants to know if any of it is worth building on. Here's the demo, module by module.

ACT 1

"Show them it won't lose their money"

The first demo is deliberately the least flashy: a transfer between two accounts, then a withdrawal that's too large, caught and reported instead of crashing or silently succeeding. The engineering lead's only question is "what happens if the second half of a transfer fails halfway through?" — and the answer, live, is: it can't, because the withdrawal happens first and nothing about the destination account changes unless it succeeds.

ACT 2

"Show them it remembers"

The second demo borrows a book, closes the program entirely, reopens it, and the book is still marked borrowed. It's a small thing to demo, but it's the one that gets a nod from the room — every prior demo this cohort gave started from a blank slate each run; this is the first one that has memory.

ACT 3

"Show them, don't just tell them"

The shape canvas demo is short on purpose — a cyan circle, a yellow rectangle, nothing more — but it's the one moment in six days of terminal output where something appears on screen instead of as text. The engineering lead's reaction says more than any explanation could: this is the first thing in the whole training that looks like a product instead of an exercise.

ACT 4

"Show them you checked, instead of assuming"

Someone in the room asks the question every demo eventually gets: "will this scale?" Instead of a guess, the answer is a number — the reserve() timing comparison, run live, showing the actual cost of the naive version next to the fixed one. It's not a huge number. That's the point: it's a real, measured one, not a hand-wave.

ACT 5

"Now defend it"

The last five minutes aren't a demo at all — they're questions. Why a delimited text file instead of a real database? Why dynamic_cast in the banking system instead of a virtual method? Every answer traces back to a specific module, a specific tradeoff, made on purpose. That's the actual skill this whole day was testing: not writing the code, but being able to explain it under questioning.

Every module in this handbook taught one idea in isolation. Launch day is the first time all of them have to hold up together, in front of people who weren't there when you wrote any of it.

struct Book { string title; string author; bool onLoan; };

Now combine the pieces into the complete use case
01
Library Management System — records, borrow/return, and file persistence together

The full Library class: add, borrow, return, list available, and save/load the whole catalog to a text file.

program.cpp — complete use case
#include <iostream>
#include <fstream>
#include <sstream>
#include <string>
#include <vector>
#include <algorithm>
using namespace std;

struct Book {
    string title;
    string author;
    bool onLoan;
};

class Library {
    vector<Book> catalog;
    string catalogFile;
public:
    Library(string file) : catalogFile(move(file)) {}

    void addBook(const string& title, const string& author) {
        catalog.push_back({title, author, false});
    }

    bool borrowBook(const string& title) {
        auto it = find_if(catalog.begin(), catalog.end(),
                           [&](const Book& b) { return b.title == title; });
        if (it == catalog.end() || it->onLoan) return false;
        it->onLoan = true;
        return true;
    }

    bool returnBook(const string& title) {
        auto it = find_if(catalog.begin(), catalog.end(),
                           [&](const Book& b) { return b.title == title; });
        if (it == catalog.end() || !it->onLoan) return false;
        it->onLoan = false;
        return true;
    }

    void listAvailable() const {
        for (const auto& b : catalog)
            if (!b.onLoan) cout << "  " << b.title << " by " << b.author << "\n";
    }

    void saveToFile() const {
        ofstream out(catalogFile);
        for (const auto& b : catalog)
            out << b.title << '|' << b.author << '|' << (b.onLoan ? 1 : 0) << '\n';
    }

    void loadFromFile() {
        catalog.clear();
        ifstream in(catalogFile);
        string line;
        while (getline(in, line)) {
            stringstream ss(line);
            string title, author, loanFlag;
            getline(ss, title, '|');
            getline(ss, author, '|');
            getline(ss, loanFlag, '|');
            catalog.push_back({title, author, loanFlag == "1"});
        }
    }
};

int main() {
    Library lib("catalog.txt");
    lib.addBook("Clean Code", "Robert Martin");
    lib.addBook("The Pragmatic Programmer", "Hunt & Thomas");
    lib.addBook("Effective Modern C++", "Scott Meyers");

    cout << "Available before borrowing:\n";
    lib.listAvailable();

    lib.borrowBook("Effective Modern C++");
    cout << "\nAvailable after borrowing 'Effective Modern C++':\n";
    lib.listAvailable();

    lib.saveToFile();
    cout << "\nCatalog saved to catalog.txt.\n";

    Library reloaded("catalog.txt");
    reloaded.loadFromFile();
    cout << "\nReloaded from disk, available copies:\n";
    reloaded.listAvailable();

    reloaded.returnBook("Effective Modern C++");
    cout << "\nAfter returning 'Effective Modern C++':\n";
    reloaded.listAvailable();
}
